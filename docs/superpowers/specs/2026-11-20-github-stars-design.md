# GitHub 星星數觀察站：設計

日期：2026-11-20
使用者：只有自己一個人看

## 要做什麼、為什麼

一個網頁，每天看一次「所有 GitHub 專案裡，最近星星增加最多的是哪些」。
GitHub 只提供每個專案「現在總共幾顆星」，不提供「這個月多了幾顆」，所以要自己每天記一次總數，用前後差距算出增加量。

## 頁面內容（使用者指定）

- 兩份前 20 名排行：
  - **月排行**：最近 30 天星星增加數（今天的總數減 30 天前的總數）
  - **週排行**：最近 7 天星星增加數（今天的總數減 7 天前的總數）
  - 都是「從今天往回算」，不是日曆上的月份或週一到週日。（設計者的判斷）
- 折線圖：顯示排行裡專案每天的星星數變化。
- 每個專案附 GitHub 上的說明文字與網址。

## 不做的事

- 不做登入、多人使用、通知、Email。
- 不做程式語言篩選、搜尋。
- 不追蹤 GitHub 上所有專案（做不到），只追蹤下面「追蹤清單」裡的專案。

## 已決定的做法

### 放在哪裡、怎麼跑
- 一個新的**公開** GitHub repo，建在 `max8568` 帳號下（使用者決定）。頁面和資料任何人都看得到，內容只有公開專案的星星數。
- 用 GitHub Actions 每天自動跑一次，資料以 JSON 檔存在同一個 repo 裡，頁面用 GitHub Pages 開。
- 每天台灣時間早上 8:30 執行（UTC 00:30），也可以手動觸發。
- 程式用 Node.js（不裝額外套件為原則，網頁解析若需要可用 cheerio）。

### 追蹤清單（要記哪些專案）
每天把以下來源出現的專案加進追蹤清單：
1. GitHub Trending 網頁 `https://github.com/trending?since=daily`、`weekly`、`monthly`（全部語言），每份約 25 個。
2. GitHub 搜尋 API：最近 30 天內建立、依星星數排序的前 100 個。

一個專案連續 30 天都沒有再出現在上述來源，就從追蹤清單移除，歷史資料一起刪掉，避免檔案越長越大。

### 每天記錄
- 用 GitHub GraphQL API 一次查多個專案（每次 50 個左右），取得星星總數、說明、網址、主要語言。
- 存成 `data/history.json`：`{ "owner/name": { "2026-11-20": 12345, ... } }`
- 專案資訊（說明、網址、語言）存成 `data/repos.json`，每天更新。

### 補過去 30 天的資料
新專案第一次加進追蹤清單時，嘗試補回過去 30 天每天的星星數：
- GitHub stargazers API 可以查每顆星是什麼時候按的，依時間由舊到新排，每頁 100 筆。
- 從最後一頁往前翻，翻到 30 天前為止，就能用「現在總數 − 某天之後按的星數」推出那天的總數。
- 限制：這個 API 最多只能翻到第 400 頁（4 萬顆星）。總星數超過 4 萬的專案補不到，只能從加入那天開始累積。
- 補不到或補一半的，頁面上照實顯示資料天數，不假裝有完整資料。

### 算排行
- 月排行：增加數 = 今天總數 − 30 天前總數。沒有 30 天前的資料時，用最早一筆，並在頁面上標「只有 N 天資料」。
- 週排行：同上，7 天。
- 結果存成 `data/rankings.json`，網頁直接讀這個檔。

### 網頁
- 單一 `index.html`，用 Chart.js（CDN）畫圖。
- 上方切換「月排行／週排行」。
- 表格：名次、專案名稱（連到 GitHub）、說明、語言、增加數、目前總數、資料天數。
- 折線圖：Y 軸是「從排行起算日到當天，累積多了幾顆星」，起算日當天為 0。切到月排行畫 30 天、月排行的 20 個專案；切到週排行畫 7 天、週排行的 20 個專案。`rankings.json` 裡兩份排行各自附上畫圖用的每日數字。20 條線太亂，所以預設只顯示前 5 名，點表格某一列可加入或移除那條線。（設計者的判斷）
- 頁面上方顯示資料最後更新時間。

### API 用量
- Actions 內建的 `GITHUB_TOKEN` 每小時 1,000 次請求。每天記錄約需 5 到 10 次 GraphQL 請求；補資料是大宗，一個月多 1 萬顆星的專案要約 100 次。
- 補資料另外寫成一個每小時跑一次的工作：每次補到用量快到上限（留 100 次給每天記錄）就停，下個小時繼續，沒有待補的專案就什麼都不做。第一天約有 175 個專案要補，這樣大約一週內補完。（設計者的判斷）
- 補的順序：Trending 本月名單上的先補，其次本週、本日，最後才是搜尋來的新專案。（設計者的判斷）

## 考慮過的做法

| 做法 | 取捨 | 結果 |
|---|---|---|
| 每次都查每顆星的按讚時間（方法 A） | 不用等累積，但熱門專案很慢、超過 4 萬顆查不到 | 只拿來補第一次的 30 天 |
| 每天記一次總數（方法 B） | 準確、快，但要累積才有歷史 | **採用** |
| 第三方服務（OSS Insight） | 現成的增加量資料，但依賴別人的服務 | 不採用 |
| 在本機用 Windows 工作排程器跑 | 不用建 repo，但關機那天就斷資料 | 不採用 |
| GitHub Actions + GitHub Pages | 關機也照跑，手機也能看 | **採用** |
